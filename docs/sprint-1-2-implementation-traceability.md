# Sprint 1–2 Mobile implementation traceability

This document maps the original Mobile Report Sprint 1 and Sprint 2 backlog
items and each story’s acceptance-criterion scenario labels to source and test
files in the Operations Android checkout. It records source evidence and the
current verification limits. A source file or test source does not prove that
an acceptance criterion passed.

## Authority and scope

The academic backlog and scenario definitions are pinned to Mobile Report
`develop` commit
[`55f959441fb4d5422519db31c380631e95ed72e3`](https://github.com/nexa-suite/mobile-report/tree/55f959441fb4d5422519db31c380631e95ed72e3).
The Product Backlog assigns Sprint 1’s six Mobile items (four functional
stories and two technical stories, 19 SP) and Sprint 2’s 30 Mobile items (21
functional stories, five technical stories and four spikes, 129 SP). The scope
mapped below is therefore 36 Mobile PBIs / 148 SP across the two original
plans. Sprint 2’s Mobile slice is 88 SP functional, 23 SP technical and 18 SP
spikes. The report’s six Landing stories are outside this Operations Android
trace. NX keys shown in the tables are cross-references from the report’s
Sprint backlog/Jira tables; they do not change which items belonged to the
original plan.

## Current architecture and verification boundary

The inspected Operations Android source tree has 11 canonical context roots
and 31 runtime context modules across eight roots. BC-08 Payments, BC-10
Notifications and BC-11 Business Traceability have context documentation but
no runtime modules. `:app` and `:core:*` are composition and technical
foundations, not additional Bounded Contexts. Client `domain` code contains
non-authoritative projections and local constraints; the API remains the
authority for business outcomes. The paths below do not imply server DDD
models or server authority in the client.

The current source checkout is branch
`feature/mobile-context-ddd-v1.1.0`, based at
`af2558bb5b2f57c3b30e74ed80c5576332802e1b`; the DDD migration working tree
contained uncommitted source edits while this mapping was prepared. Evidence
paths therefore refer to the inspected working tree and are not a claim about
an immutable release candidate.

On 2026-10-08, the resumed working tree passed
`./gradlew verifyAndroidArchitecture ktlintCheck lintDebug testDebugUnitTest :app:assembleDebug --dependency-verification strict --console=plain`
from `apps/operations-android`. The configured modules produced 114 XML test
suites containing 524 JVM tests, with zero failures, errors, or skips. The
Python context check also passed with 11 canonical roots and checked layers.
This verifies local static/JVM gates on the resumed working tree; it does not
verify an immutable candidate or every PBI acceptance scenario. Connected
Android instrumentation passed on API 37 and API 29 AVDs: each run recorded 64
tests with zero failures, errors, or skips across 13 module XML reports (eight
reports contained tests; the others were empty). Live service integrations,
physical-device behavior, and Product/System acceptance remain separate.

An earlier checkpoint failed strict dependency verification for missing
`androidx.collection:collection:1.4.2` metadata, and an earlier formatting
attempt failed on a scanner filename subsequently moved/renamed. Those failed
observations remain historical negative evidence; the later passing gate does
not erase them. The trace does not treat those failures as current blockers.

For every row, `AC scenarios` enumerates the original scenario titles. The
implementation and test links map that story’s behavior to current source.
The aggregate result above includes configured `src/test` JVM tests, including
the moved BC-05/BC-06 storage unit tests. The API 29/API 37 AVD runs include
`androidTest` instrumentation; their exact matching cases are noted below.
They do not establish live API traversal, physical-device behavior, or
acceptance of every listed scenario. A test pass does not substitute for
Product/UX or System Acceptance.

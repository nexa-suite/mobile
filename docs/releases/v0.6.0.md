# Nexa Operations Mobile v0.6.0

Corte técnico: 4 de octubre de 2026.

Esta versión publica un corte académico del cliente Android con `versionCode 7`. La compilación de depuración puede apuntar al origen HTTPS público de validación de Nexa mediante la propiedad de Gradle `nexaDebugApiBaseUrl`; el valor aprobado para esta revisión es `https://nexa-api-69bj.onrender.com/`.

Durante este corte, el servicio desplegado desde `main` respondió `200/UP` en
readiness y la dependencia de base de datos estuvo disponible. En el tenant
ICISA se verificaron 102 productos, 102 imágenes y 102 precios; la vista de
comprador mostró 50 productos y mantuvo 52 ocultos según la regla de
visibilidad. La sesión del fundador respondió HTTP 200 en el
entorno oficial. Esta evidencia confirma la disponibilidad técnica del
entorno de evaluación, sin declarar aceptación integral ni producción.

La publicación adjunta el APK de depuración `nexa-operations-v0.6.0-cloud.apk`. Su SHA-256 es `ace7c8730e54a9746634ca8780003caccb05280bb3cf0b57de64060067dde440`.

El corte integra la representación de las imágenes canónicas del catálogo
en las pantallas de productos mediante el sistema de diseño compartido, con
carga acotada por memoria y cobertura enfocada de UI y JVM.

La comprobación local estricta pasó arquitectura, formato, lint y las pruebas JVM. El APK de depuración se compiló, instaló y abrió en un emulador Android disponible, y se cerró sin dejar el proceso activo. La sesión del fundador y las cuatro sesiones de roles se verificaron contra el servicio oficial; esa evidencia corresponde al API y al entorno, y no acredita el inicio de sesión desde el APK. La ejecución en un dispositivo físico, los recorridos completos de aceptación y las capturas finales siguen siendo validaciones independientes.

Las comprobaciones focalizadas del corte en API 29 confirmaron una
ejecución de identidad y una de memoria de imágenes, ambas con 1 caso ejecutado
y 0 fallos, errores u omisiones. La comprobación de memoria recorrió las 102
imágenes canónicas; estos resultados no sustituyen la validación completa de
roles ni la aceptación en dispositivo físico.

La ejecución instrumental ordinaria realizó 54 pruebas en un emulador API 29.
En ese registro, la prueba de identidad remota quedó fuera mediante su filtro
opt-in documentado y la prueba de recorrido por rol llegó a su precondición de
credenciales, por lo que ese recorrido no acredita una validación de la UI.
Después de ese registro, la activación oficial verificó cuatro cuentas
adicionales con sesión HTTP 200 y permisos activos: WAREHOUSE consultó el único
almacén autorizado; SALES consultó sus solicitudes de compra y recibió 403 al
intentar consultar almacenes; DISPATCH consultó sus órdenes de despacho; y
LOGISTICS consultó el endpoint de entregas, sin afirmar una asignación concreta
ni crear un rol DRIVER separado.
También se verificaron el alta de almacén y cuatro permisos de almacén activos.
Esta evidencia confirma las capacidades del API y del entorno, pero no
sustituye el recorrido completo de la interfaz móvil por rol.

El repositorio incorpora un flujo manual de GitHub Actions para construir el APK de depuración con ese origen HTTPS y conservarlo como artefacto académico temporal. El APK usa la firma de depuración del proceso, no una clave de release o distribución; no contiene credenciales y no representa una publicación en Play Store ni una preparación de producción.

La readiness/liveness del servicio remoto respondió correctamente durante esta
revisión. El envío SMTP de evaluación mediante Brevo se verificó para
activación, recuperación e invitaciones. Esta evidencia confirma la entrega
en el entorno de evaluación; la confiabilidad, capacidad y monitoreo del
correo en producción todavía no se han medido. Las validaciones de cuentas y
permisos del entorno de evaluación están completas; por ello esta versión
mantiene separadas la cobertura de capacidades del API, la aceptación de la
interfaz móvil, la validación en dispositivo físico y la disponibilidad
integral de producción.
